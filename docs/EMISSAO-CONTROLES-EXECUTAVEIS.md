## Implementado e executado

- `lab/alby_guarded_proxy.py` é servidor HTTP **Unix socket**, não CONNECT. Verifica credencial sintética por FD 0600 de proprietário efetivo (sem env/argv do conteúdo), define `PR_SET_DUMPABLE=0` e RLIMIT_CORE=0, adiciona Bearer apenas na saída TLS do próprio processo, não ecoa token nem registra mensagens de exceção. Socket 0600 + `SO_PEERCRED`/UID explícito; usuário diferente é rejeitado. Cliente não pode enviar Authorization, Transfer-Encoding, headers adicionais, Host alternativo, URL absoluta, query string, path codificado/não canônico ou segundo frame HTTP. GET `/balance`, `/invoices`, `/invoices/incoming`, `/invoices/<64hex>`; POST `/invoices` apenas com opt-in em fixture, corpo JSON canônico `{amount: inteiro 1..10, memo: tcc:<ID>}`. `POST /payments/bolt11` é negado sempre. Resposta só 200 JSON pequena, redirects/error status/Location rejeitados, sem follow; timeout 5/10 s; TLS upstream com CA e hostname/SNI `api.getalby.com` verificados. Testes positivos e negativos de framing, host, JSON duplicado, método, rota, redirect, cert de outro host, UID. Segredo sintético não aparece no HTTP de resposta/stdout/stderr/argv/env; não existe promessa de segurança contra root ou memória do processo.
- **Guarda de segurança deliberada:** o proxy só conecta `127.0.0.1:<porta fixture>` e recusa credencial sem prefixo literal `synthetic-`; `main()` não inicia servidor. Não há configurador de upstream real nem listener público. Isso é um controle *executável de ensaio*, **não** uma via para atingir Alby. Mesmo com flag `invoices_enabled` ligada dentro do teste, o POST alcança exclusivamente o HTTP falso com certificado de fixture. A política é aplicada antes do TLS, não é apenas função solta.
- `lab/alby_guarded_smoke.py` rodou como root no LXC **121** dentro de `unshare --net` descartável (somente loopback), CA/certificado `api.getalby.com` descartáveis e endpoint HTTPS falso em `127.0.0.1`. ## Threat model e limitações que impedem ativação

Fronteira de confiança do ensaio: cliente autorizado pelo **UID do UDS** → processo proxy confiável com segredo em memória → conexão TLS iniciada pelo proxy para **servidor falso**. O cliente não recebe token e não escolhe host upstream. Mesmo UID ou root que controlem código, FD/socket/memória podem subverter o isolamento; `PR_SET_DUMPABLE`/RLIMIT_CORE não bloqueiam root, falhas no runtime/stdlib nem vazamento acidental em outros componentes. Execução root da fixture *não* é arquitetura de produção; isolar UID por serviço e rede é obrigatório. O FQDN de certificado gerado no teste não é certificado real Alby: prova que o código rejeita cert/SNI divergente com CA de teste, não prova trust chain da Alby real.

**LNbits upstream v1.6.2 não foi patchado**: ainda aceita `ALBY_ACCESS_TOKEN` em env/settings e pode logar settings. Passar-lhe FD não altera esse comportamento; `VoidWallet` deve permanecer. Integrar esse proxy a LNbits sem patch da fonte/HTTP client, sem segregação de UID/escopo e sem resolver chave de wallet seria inseguro. Egress default-deny foi comprovado apenas para processo de fixture numa netns sem rota, **não** para um LNbits ativo nem para o host com túnel Alby. A política atual não implementa o proxy de produção que resolve `api.getalby.com` exclusivamente para IP público, preserva CA do sistema, autentica LNbits separado e testa redirecionamentos do fornecedor sob falhas; não é correto afirmá-la pronta para tráfego com credencial real.

Condições anteriores a primeiro teste de **10 sats**: projeto/revisão de adaptador real que não injete token em LNbits; bloqueio auditado de logs/settings/admin/SQLite/filhos/ptrace/core e identidade/credenciais separadas; proxy real de método+host+valor com TLS válido e egress default-deny sustentado inclusive IPv6, DNS/cloud CDN, SIGKILL/rollback/SSH; reconciliação de órfãos e prova de identificação wallet/amount/status; backup/restauração de PG e SQLite. Apenas **depois** pedir consentimento expresso identificando LXC 121/conta, rede, uma invoice potencialmente pagável de exatamente 10 sats, teto de perdas, pagador/taxas, janela/rollback e autorização **separada** para eventual pagamento. Próximo passo concreto: desenhar e revisar o adaptador LNbits↔UDS com fixture sintética e teste de fuga de settings/logs no processo real, preservando `VoidWallet` no launcher padrão. Nenhuma dessas condições foi implicitamente aprovada pelo escopo de criação do token.
